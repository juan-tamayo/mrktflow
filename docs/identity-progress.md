# Identity implementation progress

## T008 backend account and invitation slice — October 10, 2026

T008 remains open. No staff login, owner form, invitation delivery/acceptance screen, or staff management route is exposed by this slice. Administration remains closed. Customer accounts, staff 2FA and sensitive-action reauthentication belong to later slices and remain launch requirements.

Implemented:

- Independent UUID staff principals and a fixed staff session provider. Session storage accepts UUID principals; rollback discards volatile sessions rather than converting UUIDs into numeric identities.
- Atomic first-owner creation and installation completion. The platform holds its installation lock while the application supplies the identity write callback; platform never imports identity. Invalid credentials or extra role/permission fields roll back the owner, lock and audit intent together. Successful creation revokes setup secrets and grants permanently.
- Server-owned permission registry and owner/manager/content-editor/fulfillment presets. Gates reject inactive staff, unknown abilities and other principal classes even when email or role fields match. Customers will receive their own table and guard in T009.
- Staff access changes re-read the actor under a shared security row lock, protect the final active owner, and increment a session version while clearing remember tokens. Session-version enforcement comes with the login middleware; this slice does not claim existing HTTP sessions are already invalidated.
- Invitations bind one canonical email and an explicit preset permission snapshot. Secrets have 256 bits of randomness, only SHA-256 digests persist, expiry is 48 hours, and acceptance consumes the token atomically with account creation. Reissuing revokes prior unused invitations. Acceptance rechecks the inviter's current staff-management permission. Possession alone does not mark email verified.
- Passwords use the configured Laravel bcrypt hasher, minimum 12 characters and maximum 72 bytes to prevent silent bcrypt truncation. Confirmation is required. No generic signup or password-reset broker is enabled.
- Security audits record UUID subjects, actors and session version only; no email, password or invitation secret enters audit metadata. Invitation JSON serialization excludes the one-time delivery secret.

Its DTO is not a signed token or bearer credential; a caller must prove identity again for every claim. ## Verification and password-recovery token protocol — T009 in progress

Customer verification and recovery now have separate internal domain actions and durable `customer_challenges` records. A 256-bit random secret is returned once to the application delivery layer; the challenge table stores only its SHA-256 digest, purpose, customer UUID, canonical-email digest, session version, expiry and consumption/revocation timestamps. Verification expires after 24 hours and password recovery after one hour. JSON/debug representations exclude the secret, and PHP serialization of the credential DTO is rejected. Do not log the DTO or its explicit `token()` result.

Reissuing a purpose revokes the previous unconsumed challenges of that purpose. Unknown, inactive and staff-only emails do not create a customer recovery challenge. Verification issuing requires the current active customer actor; verification consumption additionally requires the authenticated actor to match the token-bound account/email/version. Recovery only changes the bound customer password; it neither modifies matching staff records nor automatically sets email verification. Existing verified status is preserved during recovery.

Issuers and consumers lock the customer row before challenge rows. Consumption rechecks purpose, expiry, email, active state and version under locks; malformed, expired, superseded, replayed or differently scoped tokens fail without changing the account. A successful verification or reset increments the customer session version, clears remember-token state, consumes its own challenge and revokes all remaining outstanding challenges. Account changes, token consumption/revocation and minimal audit intent are atomic. Existing customer middleware rejects the previous session versions. Verification's eventual controller must establish only the current verifying browser using the returned account; recovery must return to sign-in rather than automatically acquiring a staff/customer session.

Ten new tests include a real two-process MySQL race against one recovery token: only one password wins, version advances once, one audit intent is created, and the second consumer is denied. Other cases cover email/version changes, wrong accounts/purposes, expiry, reuse, unknown/staff-only emails, injected fields, password byte limits, secret serialization and rollback when audit intent cannot be recorded.

This is the token protocol, not the completed email workflow. There are no new public recovery/verification routes or email sends in this slice. Next, an application coordinator must wrap issuance plus an encrypted, durable email-delivery intent in one outer transaction, and queue only its ID. Network email must run outside local outbox consumer transactions; never use the default log mailer for credential links. Confirmation GET requests must not consume a token, and credentials must not be reflected into HTTP responses, logs or flashed input. Generic recovery responses and bounded request counters belong to those upcoming HTTP handlers. T009 remains unchecked; T079 still owns full transactional-mail configuration, failures and operations.

Final local evidence for this token-protocol slice: 166 PHP tests (982 assertions), 13 Vue tests, and 10 existing Chromium journeys passed. Pint, PHPStan level 8, TypeScript, ESLint, Prettier, production build and whitespace checks passed. Browser evidence covers regression of currently mounted signup/sign-in/staff/setup pages, not the still-unmounted verification/recovery UI. The additive challenge-table migration was also applied to the positively checked isolated development database; no account password or verification state there was modified.

## Durable customer credential mail — T009 in progress

The internal application coordinator now wraps challenge issuance and encrypted delivery intent in one transaction. The database stores an authenticated encrypted email/token payload until delivery acknowledgement or expiry; queue jobs contain only a delivery UUID and are themselves encrypted. Publication failures leave recoverable intent. A bounded scheduled recovery pass publishes due work and removes expired credential payloads, including terminal failures.

The sender checks the current customer, challenge, email digest, version, expiry and payload binding under locks, then sends outside the database transaction. Superseded, consumed or changed-account challenges are cancelled. A claim lease prevents concurrent active sends; acknowledgement checks the claim UUID before changing state. Successful sends erase the encrypted payload. Failures use generic codes, bounded delays and at most six automatic attempts. Logs contain IDs and exception class names, never exception messages, recipient addresses or tokens.

Delivery requires the merchant sender settings and a configured application URL. SMTP requires TLS, peer validation and a timeout of at most ten seconds; transport URL overrides are refused. The log transport and unreviewed fallback/provider transports are refused. The array transport is accepted only in the guarded testing environment. Message links carry credentials in the fragment, and use configured APP_URL rather than request Host. The fixed Blade template escapes values and also provides a code for a future native confirmation form.

A worker crash after SMTP acceptance and before database acknowledgement can cause a duplicate email on recovery. SMTP cannot provide an exactly-once acceptance guarantee; a stable message ID does not guarantee provider deduplication. The repeated link still has the same single-use token. Already in-flight mail cannot be recalled when a later challenge supersedes it; consumption rechecks current validity. Active leases are excluded from expiry cleanup until the lease ends.

Private commands provide bounded recovery, payload-free counts and explicit retry of an unexpired failed delivery after repair. These are identity-specific delivery primitives; general transactional/marketing mail configuration, provider adapters and administration remain T079. Public recovery/verification forms and registration/resend integration are still unmounted, so this slice sends no live customer links to unfinished screens. T009 remains unchecked.

Verification covers encrypted persistence, outer rollback, publication outage, actual array transport acceptance, real database queue execution, replay, supersession, simulated abandoned leases, bounded transport failures, expired cleanup, explicit retry, unsafe configuration and corrupt/mismatched payloads. The lease recovery test simulates an abandoned claim; it is not evidence of a killed SMTP worker or live provider acceptance.

## Editable profiles and encrypted saved addresses — T009 in progress

Customers now edit their name/email through `/account/profile`. A revision number rejects stale writes rather than silently overwriting another device's change. Name-only edits preserve verification and customer session version. A changed canonical email requires the current password, checked before taking locks and bound to the current password hash under the account lock. Email changes clear verification/remember state, increment session version and revoke outstanding challenges. The HTTP application transaction includes profile change, ID-only audit and new verification-mail intent; the current browser rotates into the new version after commit, and previous versions are rejected by customer middleware. Canonical uniqueness failures return a generic email-save error. Injected permissions/active/verification fields are rejected.

Saved addresses have UUIDs, a customer foreign key with cascade deletion, revision and authenticated encrypted JSON payload. The ciphertext envelope binds both customer UUID and address UUID; swapping a valid ciphertext into another row is rejected before rendering. An ownership-scoped domain service rechecks the current active customer/version/email and locks the customer before reading or changing address rows. All writes for one customer's addresses share that lock, including the 20-address cap. Edit/delete compares the stored revision; foreign and missing UUIDs return 404, and stale revisions return 409. Deletion removes the encrypted payload immediately. Audit intent stores IDs, action and revision only; personal address fields never enter the event payload. Encryption relies on the application key and does not replace account authorization. Export/deletion and backup retention still belong to T083.

Fields are limited to label, recipient, street lines, city, region, postal code and country. No phone number or extra demographic fields are collected. Countries use the existing platform country catalogue. Region/postal code are optional rather than imposing one country's address format. Saved-address countries are not shipping permission; checkout must recheck current merchant shipping eligibility later. The bounded list exposes only explicit address fields, ID and revision, never ciphertext, keys or arbitrary JSON fields.

Server-rendered profile/address forms work without JavaScript, escape values, use POST/CSRF, retain private/no-store/noindex/no-referrer headers and have separate request limits. ## Privileged staff two-factor authentication — T013 October 13, 2026

Owners and staff with `settings.manage`, `integrations.manage`, `orders.refund`, or `content.publish` must complete TOTP enrollment before `/admin`, `/admin/staff`, and theme preview. Fulfillment and content-editor presets stay optional. The authenticator profile is SHA-1, 6 digits, 30-second period, 160-bit secrets, ±1 period window, using locked `spomky-labs/otphp` 11.5.0. Pending enrollment expires after 15 minutes.

Secrets and recovery-code hashes are encrypted with a staff-UUID envelope; swapped ciphertext fails closed. Ten recovery codes are shown once, hashed at rest, and each is single-use. Using a recovery code wipes the authenticator so a lost device must enroll again. TOTP codes cannot be replayed in the same time step. Staff access changes and invitation creation require a password plus authenticator confirmation that lasts 15 minutes.

Login, first-owner creation, and privileged invitation acceptance redirect to `/admin/two-factor`. Logout remains available during enrollment and challenge. Recovery codes, secrets, and TOTP values are excluded from flashed input and from JSON serialization of the enrollment DTO. Audit intent records enroll/replace and recovery use with reason codes only.

Remaining gaps: no QR image (manual secret and otpauth URI only); optional 2FA is not offered to non-privileged roles; refund and credential-change screens do not exist yet, so reauthentication is wired to staff mutations only; hosted Quality CI was not run here.
