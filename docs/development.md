# Development

The secure foundation is runnable. The unopened storefront homepage returns HTTP 503; unconfigured administration stays closed until protected setup finishes. A private CLI installation secret unlocks store settings and first-owner creation. After permanent installation completion, the staff workspace/invitations and separate customer signup/sign-in/account screens are available. Staff with catalog permission can save nested categories and simple physical products; published category and product pages render server-side while drafts stay private. Checkout quotes collect contact and destinations; payable orders and storefront launch remain in the ordered backlog; customer verification/recovery screens are available; editable profiles and encrypted saved addresses are available; guest-resource transfer remains in progress. Framework scaffolding comes from laravel/laravel v13.11.0; installed framework is 13.35.0.

## Runtime and installation

Use PHP 8.4, MySQL 8.4, Node 22.23.3 and npm 10.9.9. `bin/php` selects the existing Homebrew PHP 8.4 on this machine, or `MRKTFLOW_PHP` elsewhere. `bin/composer` runs Composer with that same PHP; using the globally selected Composer PHP can select the wrong version. `bin/npm` selects an ignored project Node runtime if present, otherwise the pinned runtime must be on PATH. No global runtime replacement is needed.

On a fresh checkout, create private environment files and provision the isolated databases before commands that boot the app. Copy `.env.example` to `.env` and `.env.testing.example` to `.env.testing`; never overwrite an existing app key. Generate a separate key for each fresh environment with `bin/php artisan key:generate --env=testing` or without the flag for development, after dependency installation and database setup. The test guard runs on boot, so valid database settings must precede key generation. Make environment files mode 0600.

Install lockfiles first with hooks disabled:

```sh
bin/composer install --no-scripts --no-plugins
bin/composer check-platform-reqs
bin/composer dump-autoload
bin/npm ci --ignore-scripts
```

The approved Laravel autoload/package-discovery hooks and Pest plugin are documented in [security foundation](security-foundation.md). npm lifecycle scripts remain disabled by `.npmrc`. Initial scaffold instructions for optional Boost/AI tooling were replaced with the project's own AGENTS.md; those tools are not dependencies.

## Database isolation

Provision three distinct databases and users named `mrktflow_dev`, `mrktflow_test` and `mrktflow_browser`, each with a fresh random password and privileges on only the matching database. Do not grant global permissions, roles or GRANT OPTION. Enable `partial_revokes=ON` **before granting permissions** so underscores in these names are literal rather than wildcard grants. Use MySQL 8.4. Do not use a merchant database or root account for application/test commands.

On this machine the already provisioned server lives in ignored `.runtime/mysql`, communicates through its private socket, and has networking disabled. Start it in a separate terminal with `bin/local-db start`; stop it with `bin/local-db stop`. The latter reads the private admin configuration without passing its password on the command line. `MRKTFLOW_MYSQL_BIN` selects an equivalent MySQL 8.4 executable directory on another machine. This helper never initializes or resets data; a new machine must provision its own isolated instance and random credentials. Do not copy local database data or secrets into the repository.

The PHP test guard checks environment, connection overrides, actual server version/database and account grants before any test schema operation. Cached configuration is forbidden. Tests use array mail and a synchronous default queue. The outbox interruption fixture alone runs an explicit database queue on the guarded test database; no external provider credentials are needed.

For browsers create `.env.browser` from the testing template, with database and username `mrktflow_browser`, its own password/key, `APP_ENV=testing`, `APP_URL=http://127.0.0.1:8011`, `SESSION_DRIVER=database`, `CACHE_STORE=database`, `QUEUE_CONNECTION=sync`, `MAIL_MAILER=array`. Playwright supplies these values to a separate server and resets only that database. Do not use `--env=browser`: Laravel interprets it as an environment identity, which the guard rejects.

## Customer verification, recovery and credential mail

Signup queues confirmation mail atomically. Customers can resend from their account, confirm through `/account/verify`, request recovery at `/account/forgot-password`, and submit a new password through `/account/reset-password`. GET screens never consume tokens. Links fill a credential field from a fragment and remove that fragment from history; manual email codes also work without JavaScript. Only POST forms consume codes. Recovery returns a generic result and is limited by canonical email and IP; confirmation resends are limited by customer and IP. The default log mailer is deliberately refused for credentials. Configure reviewed SMTP with MAIL_MAILER=smtp, MAIL_HOST, MAIL_PORT and provider credentials in the private environment; TLS and certificate validation remain required by configuration. MAIL_URL overrides are refused. Sender name/email come from store settings, and links use APP_URL (HTTPS in production). Never include credentials in diagnostic output.

Run the identity lane independently of local outbox consumers:

```sh
bin/php artisan queue:work database-outbox --queue=identity-mail --timeout=60 --tries=1
bin/php artisan identity:mail-recover
bin/php artisan identity:mail-health
bin/php artisan identity:mail-retry <delivery-uuid>
```

The normal scheduler runs bounded recovery every minute. Configure a supervised worker and reviewed SMTP before opening the store to customers; signup can succeed while mail awaits repaired configuration. SMTP timeout is ten seconds, the delivery claim lease is 120 seconds, and queued publication is leased for 90 seconds. Worker retry is one because the durable delivery record owns bounded retry scheduling. Health reports private counts only; it is not a provider delivery guarantee. A retry requires a failed, unexpired encrypted intent and sending rechecks challenge eligibility. Tokens expire after 24 hours for verification and one hour for recovery. Expired payloads are erased by recovery, including terminal failures. Preserve the application key securely: encrypted pending deliveries depend on it.

A crash after transport acceptance can produce a duplicate email when the lease expires. Single-use challenge consumption remains authoritative; no exactly-once SMTP promise is made. A log/array transport must never be used as successful delivery in production; array is test-only.

## Theme registry and compatibility

Installed developer themes register through `ThemeRegistry` (`RegisterTheme`) before any activation exists. `PlatformVersion` is the platform's version source — core `1.0.0`, theme API `1` — and evaluates the bounded range grammar manifests declare: whitespace-separated comparator tokens (`>=1.0.0 <2.0.0`) that must all hold, where a bare partial version pins the precision it declares (`1` means `>=1.0.0 <2.0.0`, a full `1.2.3` pins exactly); anything outside the grammar is unparsable and can never pass silently. Registration reads `theme.json` from a theme directory under the themes root, rejects unknown manifest fields, and validates every declared template and asset path at registration time: paths may be theme-relative or root-relative naming this theme, traversal segments, absolute paths, schemes, remote entries and symlink escapes are refused, and every referenced file must exist — a missing file fails registration naming the template/asset key and the missing file. The outcome is recorded in `installed_themes` as an explicit `valid`/`invalid` status with the specific reasons and the manifest checksum, plus a platform audit; re-registering the same directory revalidates in place, while a theme id already registered from a different directory is refused. Only a `valid` registration is activatable (`ThemeRegistry::isActivatable`); activation itself is T068. The default theme's manifest declares the documented `requires.core` range alongside `themeApi` and registers valid through the same path. Run `bin/php artisan test --filter=ThemesContentRegistry`.

## Storefront layout and system slots

The slot contract lives in `SystemSlots` (page keys, templates, slot kinds/regions/views) and `ComposePage` enforces it on every layout render through the `ThemeServiceProvider` layout composer: slot assignments supplied as view data (`slotViews`) that name an unknown slot or a platform slot throw `SlotCompositionRefused`. The masthead/footer partials stay the default theme's chrome implementation, included by the layout at the contract positions; the product preview keeps its admin chrome through the layout's preview branch. System pages (customer sign-in/registration, unsubscribe, watch verification) deliberately stay on platform views. Run `bin/php artisan test --filter=StorefrontTheme`.

## Section editor and draft preview

Staff with `content.read` open `/admin/content-editor`; saving a draft requires `content.write`, enforced server-side on every endpoint (the page only reflects the gates). A draft is one working document per (page, slot) in `content_drafts`, where the targets derive from the T062 slot contract (`SectionDraftTargets`): a known storefront page and one of its theme slots in the announcement or main region — platform slots, the head slot and unknown pages are refused before validation. `SaveSectionDraft` runs the payload through T063's `ValidateSections` first: an invalid payload persists nothing, and a valid save stores the normalized payload with binding references only (the validator's resolved summaries are render-time data, never document state), increments the document `version`, refuses a stale expected version with a conflict carrying the current state, and writes one platform audit. A rejected save returns T063's errors grouped per section (`SectionValidationErrors` — keyed by section id, or document position when the id itself is invalid) plus document-level errors, so the editor keeps its working copy, shows each problem on the block that caused it, and can fix and re-save. The editor UI generates its settings forms from the registry's typed field definitions (no per-block hardcoded forms), adds only registry block types (types at their per-page repeat limit are disabled), and reorders with native controls or Alt + arrow keys — focus follows the moved section and every change is announced in a `role="status"` region. Preview posts the working payload to `/admin/content-editor/preview`, which renders it through T063's `RenderSections` and returns the real sections fragment; the device controls change only the preview frame's width, and previewing persists nothing. Revisions and explicit publication remain T067; page/article records remain T065. Run `bin/php artisan test --filter=ThemesContentEditor` and `bin/npm run test:unit -- --run`.

## Typed product schemas

Authorized staff with `catalog.write` create versioned schemas at `/admin/schemas`. A schema has a stable key, comparison group, and typed fields (text, integer, decimal, boolean, date, or enum) with required/comparable/filterable flags. Attribute keys are globally unique in meaning: a later schema cannot reuse `sensor.megapixels` as a different type. Products may assign the current schema version and must supply valid values; invalid numeric, enum, and missing required values are rejected. Public product pages show those fields as escaped text. When products already use a schema, staff preview a new version (affected products, invalid values, comparison/filter changes) and apply it only when conversion succeeds; a failed conversion keeps the prior version and values.

## Cart ownership

Guests and signed-in customers keep separate carts until the shopper signs in or registers. Login merges the current guest cart into the account cart: matching physical variants sum and clamp to the allowed maximum, digital quantity stays one, and the shopper sees an adjustment notice. Logout invalidates the session so the account cart is no longer visible on that browser. `GET /cart` and `GET /store-api/v1/cart` return the current revision and catalog-priced lines. `POST /store-api/v1/cart/lines` replaces a variant quantity absolutely (never increments); `PATCH` and `DELETE` of a line ID require the same expected revision. Stale revisions return 409. Invalid, unpublished, out-of-stock, and unavailable variants are rejected; digital quantity is one; posted prices are ignored. Adding to cart does not reserve stock. Privileged staff still must pass 2FA before catalog admin. `GET /` remains HTTP 503.

## Money and deterministic price engine

Without a tax context, tax on the quote remains zero. Cart HTML still uses catalog regular prices. Privileged staff still must pass 2FA before catalog admin. `GET /` remains HTTP 503. ## Physical and mixed-cart shipping quotes

`ShippingQuoter` quotes immutable physical-line snapshots: destination zones, include/exclude shipping classes, discounted physical merchandise subtotals, and integer gram weights. Digital-only baskets quote zero shipping without an address or method. Mixed carts ignore digital lines for charges, free-shipping thresholds, and class coverage. Unsupported destinations or mixed classes that no single method covers fail with no-service; missing weights fail weight tables without inventing grams. Local pickup skips the delivery address and uses the configured pickup location as the physical tax destination, with instructions and no stock promise. The quote freezes method/rule revision, charge, and a SHA-256 fingerprint so later rule edits do not change that snapshot. Checkout quotes collect a delivery address when physical lines need one. Privileged staff still must pass 2FA before shipping admin. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=ShippingQuote`.

## Tax configuration and deterministic calculation

Authorized staff with `pricing.manage` configure tax classes, destination rules, shipping tax class, and exclusive or inclusive price mode at `/admin/taxes`. Rules match country, optional region, and postal patterns. Equal-specificity overlapping destinations are rejected at save; draft rules do not participate. Physical lines use the shipping destination and digital lines use billing. Exclusive tax is round-half-up(discounted base × n/d) per line then summed; inclusive tax is round-half-up(gross × n/(d+n)) and displayed without adding it again to the grand total. Documented USD fixtures: exclusive 2250 merchandise + 300 shipping at 10% → tax 255, total 2805; inclusive 2200 + 330 → tax 230, total 2530. Zero-rate rules must be explicit; missing or ambiguous coverage fails closed. Staff can preview physical, digital, and mixed carts without opening checkout. Checkout quotes apply `TaxContext` from billing and shipping destinations and fail closed on missing coverage. Privileged staff still must pass 2FA before tax admin. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=PricingTax`.

## Immutable checkout intent

`POST /store-api/v1/checkout-sessions` with an `Idempotency-Key` claims one payable order per cart revision from an accepted quote. The transaction freezes quote, line, and address snapshots, holds tracked stock and coupon usage, and creates a `pending` order with a `created` payment attempt. The same key replays; a changed payload returns 422; a second key returns the existing intent and cannot create another payable order. Failed holds roll back the order. Zero-total digital orders complete locally (`confirmed` / `succeeded`, provider `local`) without a Stripe charge. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. ## Hosted payment adapter

## Verified durable webhook inbox

`POST /webhooks/stripe` is CSRF-exempt and verifies the raw Stripe-Signature HMAC, timestamp window, configured account, and livemode/environment before inserting a unique encrypted `provider_events` row. A replay of the same signed event returns 2xx without a second row. Invalid signatures or environments return 400 and store nothing. Persistence failure returns 503 so the provider can retry. The inbox does not mark an order paid by itself. `ProcessPaymentEvent` is an ID-only encrypted job on the payments queue that queries the provider session and confirms only a matching capture. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=CheckoutOrdersWebhook`.

## Payment confirmation and reconciliation

Verified matching success commits stock and coupon holds, records one `payments` capture, confirms the order, and emits `checkout.order.paid` once (`intent_key` `order:paid:{orderId}`). Duplicate inbox jobs and later expired/unpaid observations cannot downgrade that success. Unknown attempts are queried through `ReconcilePayment` and a bounded `payments:reconcile` scheduler job. A crash after the provider reports capture and before the local commit is recovered by the same query path; return URLs still cannot mark an order paid. Amount, currency, account, and live/test mismatches stay unpaid. Live Stripe capture evidence remains pending. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=CheckoutOrdersReconciliation`.

## Checkout expiry and late-success recovery

Due `created`/`awaiting_payment` attempts are expired through `ExpireCheckout` and a bounded `payments:expire` scheduler job. Open provider sessions are retrieved then cancelled with Stripe `expire` before stock or coupon holds are released; already-expired unpaid sessions may release. Unknown or failed provider responses keep holds and leave the attempt payable for later reconcile. After a verified unpaid expiry, late matching success re-reserves and commits holds when stock remains, or records the capture, marks the order `on_hold`, and writes a staff audit (`audit:order-hold:{orderId}`, reason `late-success-stock`) when a competing purchase already took the last unit. Live Stripe expiry races remain pending. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=CheckoutOrdersExpiry`.

## Order cancellation workflow

Staff with `orders.manage` submit `POST /admin/orders/{id}/cancellation` with an idempotency key and reason. Paid unshipped orders claim remaining captured money as a `cancellation` refund, hold remaining quantities, then refund outside locks; success cancels those quantities, releases committed unshipped stock once, marks the order `cancelled`, revokes undelivered digital eligibility (`download_status` `revoked`), and emits `checkout.order.cancelled` once (`intent_key` `order:cancelled:{orderId}`). Replays of the same key and later keys after success do not create another refund or event. Coupon redemptions stay committed. Any shipped quantity refuses cancellation and requires the return path. Zero-total orders skip Stripe, still cancel remaining quantities, and emit the same fact. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. Live Stripe refunds were not executed. Run `bin/php artisan test --filter=CheckoutOrdersCancellation`.

## Order timeline, receipts and customer view

Paid-order consumers record an immutable `order_events` timeline and one event-derived `order-receipt` intent (`intent_key` `receipt:paid:{orderId}`). Redelivery of the same paid event does not create another intent. Staff with `orders.manage` can queue an explicit resend (`receipt:resend:{idempotency key}`) that is audited (`audit:order-receipt-resend:{intentId}`) and does not replay the original event. Signed-in customers read their own orders at `/account/orders`; another customer's UUID returns 404. Receipt HTML uses frozen line and total snapshots. This slice queues receipt intent only and does not send SMTP. Privileged staff still must pass 2FA. `GET /` remains HTTP 503. Run `bin/php artisan test --filter=CheckoutOrdersReceipt`.

## External refunds and disputes

Signed `refund.created`/`refund.updated`/`charge.refunded` and `charge.dispute.*` events land in the same T036 inbox; `ProcessPaymentEvent` routes them to `ReconcileExternalAdjustment`, which binds strictly by the payment-intent reference stored as the local capture ID. Currency mismatches, amounts above the capture, and unbindable observations record nothing. An observation matching a staff refund (provider refund ID or `metadata.refund_id`) reconciles that row through `ApplyRefundOutcome`; any other succeeded refund becomes an immutable `origin = provider`, `kind = external` refund fact that projects `financial_status`, appends one `external_refund` timeline entry, and consumes the same refundable bounds as staff refunds — staff cannot refund money the provider already returned, and no staff path edits provider rows. The staff `payments:reconcile-refunds` job only reconciles `origin = staff` rows; provider rows settle through later provider events. A recorded dispute sets `orders.dispute_status`, holds a confirmed order (`on_hold`, with hold provenance on the dispute row), suspends entitled downloads, and writes `dispute_opened` history. A won dispute restores only the hold/suspension that dispute caused and only while access is still eligible (not cancelled, not fully refunded). A lost dispute writes one provider debit fact inside refundable bounds, revokes downloads, and projects financial status. Dispute facts are monotonic: closed-before-created, created-after-closed, and duplicate deliveries never regress or double-apply. Admin order detail shows refund origin, dispute status, and dispute facts as read-only provider history. Privileged staff still must pass 2FA. `GET /` remains 503. Live Stripe refund/dispute events were not executed (no test credentials). Run `bin/php artisan test --filter=CheckoutOrdersExternalEvent`.

## Shipments

Staff with `fulfillment.manage` record shipments at `POST /admin/orders/{id}/shipments` with a stable idempotency key (fresh staff 2FA required). `CreateShipment` locks the order and its lines and accepts only physical lines on a confirmed order with captured payment, within `quantity − shipped − cancelled − held` per line, so refund-held and already-shipped quantities can never ship. One transaction inserts the `shipments`/`shipment_lines` facts, increments `shipped_qty`, consumes tracked stock through the allocator `ship` mutation (untracked lines move no stock), projects `fulfillment_status` (`unfulfilled` → `partially_fulfilled` → `fulfilled`) from physical line quantities, records one deduplicated `shipment_created` timeline event — the durable notification intent for this slice — and writes a staff audit (`audit:order-shipment:{shipmentId}`). Replaying the same key returns the existing shipment without moving stock twice; the same key with a changed payload conflicts. Two racing submissions for the same remaining quantities ship once. Admin order detail exposes per-line `shipped_qty`/`shippable_quantity` and the read-only shipment history. Returns remain T048. Run `bin/php artisan test --filter=FulfillmentShipment`.

## Shipment tracking and notification

Tracking URLs are staff-entered and customer-rendered, so a `TrackingUrl` policy guards them at write and read time: only absolute http/https URLs on a dotted public hostname are accepted — other schemes (`javascript:`, `data:`, …), scheme-relative URLs, embedded credentials (userinfo), whitespace/control/backslash/quote characters, IP literals and single-label hosts are rejected and persist nothing. The admin shipment form validates the same rule, and customer reads re-validate stored values, so a URL recorded before the policy existed is never exposed or rendered as a link. Shipment creation queues one deduplicated notification intent per shipment in the same transaction (`shipment_notification_intents`, `intent_key` `shipment:{shipmentId}`, template `shipment`, mirroring the receipt intents) and records a `shipment_notification_queued` timeline event; replayed creations and repeated queue calls return the existing intent. The `mail.shipment` view renders the order number, carrier/tracking and only the quantities in that shipment (partial shipments show partial quantities) with the validated tracking link, and signed-in customers see each shipment with its tracking link on `/account/orders/{id}`. This slice queues intent only and does not send SMTP; the post-checkout `order-status` page intentionally shows no tracking because no shipment can exist at confirmation time. Run `bin/php artisan test --filter=FulfillmentTracking`.

## Returns and deliberate restock

Staff with `fulfillment.manage` run returns from the admin order page as four separate, individually idempotent steps (fresh staff 2FA required): open a return at `POST /admin/orders/{id}/returns` with per-line quantities and a required reason, then `POST /admin/orders/{id}/returns/{returnId}/approve`, `/receive` and `/restock`. `RecordReturn` locks the order and its lines and accepts only physical lines on a confirmed, on-hold or completed order within `shipped − committed` per line, where a return commits its requested quantities while `requested`, its approved quantities once approved, and only what it received once rejected — so the same shipped unit can never be promised to two returns. Approval records per-line approved quantities (zero rejects the line; all zero rejects the return and frees its quantities). Receipt records per-line received quantities within the approved remainder and moves the return to `received` (or `partially_received`); it never moves stock or money. Restock is a deliberate separate action: it records per-line restocked quantities within the received remainder and returns tracked units to `on_hand` exactly once through the allocator `restock` mutation keyed by the staff submission (`restock` stock movement, reserved untouched; untracked lines record quantities without inventing a balance). A refund never restocks, and a return never records money. Each step writes its own timeline event (`return_requested`/`return_approved`/`return_received`/`return_restocked`) and staff audit; replaying a step key returns the existing record without a second effect and a changed payload under the same key conflicts. Admin order detail exposes per-line `returned_qty`/`restocked_qty`/`returnable_quantity` and the return summary — status, reason and per-line stage quantities — with refund linkage: the refund facts (`refund_lines` joined to `refunds`) recorded against each returned line, read from the T041/T044 refund machinery. Run `bin/php artisan test --filter=FulfillmentReturns`.

## Digital entitlements

Paid and free-completed digital lines issue durable entitlements through an independent outbox consumer (`fulfillment.entitlements` on `checkout.order.paid`, alongside the receipt consumer). `IssueEntitlements` treats the event as a trigger only: it requires a recorded `payments` fact (a captured provider payment or the local zero-total completion row — order placement alone never grants), locks the order and its digital lines, and rechecks current eligibility before writing one `entitlements` row per digital line, pinned to the asset version frozen on the line at purchase (later asset versions never move an existing pin) and snapshotting the grantee (`customer_id`, null for guest orders). A fully refunded line, a cancelled order, a whole-order refund or a lost dispute records a durable `revoked` tombstone instead of access — a refund processed before issuance stays effective even when the paid event is delivered or replayed afterwards — and an open dispute or suspended download state records `suspended`. Amount-only goodwill refunds retain access. Re-issuance returns existing rows unchanged (a revoked entitlement is never silently reactivated), and issuance never un-suspends a `suspended` `download_status`; each paid event that creates rows records one deduplicated `entitlements_issued` timeline entry. Download areas, streaming grants, revocation of issued entitlements and expiry are separate later slices. Live Stripe sandbox purchase inspection was not executed (no test credentials). Run `bin/php artisan test --filter=FulfillmentEntitlement`.

## Download areas and guest-order claiming

Signed-in customers see their downloadable files at `/account/downloads`; guests reach one order's files at `/orders/{orderId}/downloads` after proving ownership of the order's email. Both areas list only `active` entitlements whose pinned asset version is `ready`, showing the line title/SKU plus the asset label, version and byte size — storage keys and checksums are never rendered — and suspended, revoked or expired entitlements show no files. Guest access starts at `/orders/download-access`: requesting access with an order ID and the order's email queues a `download-access` mail intent and stores only a SHA-256 digest of a 256-bit token (24-hour expiry; requesting again revokes the previous token), and every mismatch returns the same generic response so the form cannot enumerate orders. Opening the emailed link (or any scanner/prefetch GET) only renders the confirmation form and never consumes the token, authenticates or mutates state; the explicit CSRF-protected confirmation POST consumes the token atomically, rotates the session and records a grant scoped to that single order for 24 hours, after which replaying the token fails. A verified account claims historical guest orders with the explicit POST `/account/downloads/claim`: identity is re-proven inside the claim transaction, matching is on the canonical email, and claiming atomically sets `orders.customer_id`, clears `guest_token_hash`, repoints unclaimed entitlements' grantee snapshot and revokes outstanding guest tokens. An unverified registration with the same email — or merely holding a guest token in the browser session — never claims or links an order. Streaming download grants remain T051. Run `bin/php artisan test --filter=FulfillmentDownloadIdentity`.

Download areas offer each file's remaining allowance (default five per entitlement) with a POST-only issue form. Issuing a download grant stores only a SHA-256 digest of a 256-bit start token (five-minute window, bound to the entitlement, order and principal) and spends nothing; the owner-only grant page's explicit CSRF-protected start POST consumes it, rechecking principal, current entitlement/version/order eligibility and the allowance under the entitlement row lock, so concurrent starts for the last allowance create exactly one transfer session. A transfer is bound to the principal and the pinned asset version for an absolute one hour; the grant page is the lost-response recovery (it exposes the started transfer, and replaying the start POST creates nothing and spends nothing), and the five-minute token expiry never interrupts a started transfer. The stream route serves bytes from the private disk through the application — never a redirect to a storage key — with bounded single-Range support (206/Content-Range, 416 for unsatisfiable ranges, malformed or multi-range headers ignored), one concurrent stream per transfer via a short lease, and a per-request eligibility recheck: revoked/suspended entitlements, revoked transfers and other principals' requests are rejected, expired transfers return 410, and resume inside the hour spends no further allowance. Revocation blocks later requests only; already-transferred bytes are never claimed recallable. Run `bin/php artisan test --filter=FulfillmentDownload`.

Refund and dispute facts revoke or suspend issued download access in the same transaction that records them. `RevokeEntitlements::syncForOrder` locks the order, its lines and its entitlements and recomputes each non-terminal entitlement from current facts: order cancelled, any lost dispute, `financial_status` refunded, `download_status` revoked, or the entitlement's own line with `refunded_qty` at its quantity revokes; an open dispute or a suspended download projection suspends; otherwise the entitlement is eligible. Revoked and expired rows never move, and a suspended row restores only when the recomputation says eligible again. The sync runs from `ApplyRefundOutcome` (succeeded staff quantity, goodwill and cancellation refunds, including provider observations of staff refunds), from `CancelOrder::complete` (zero-total and otherwise unrefunded cancellations) and from `ReconcileExternalAdjustment` (provider refund success and dispute opened/won/lost effects). Revoking an entitlement revokes its unconsumed grants (`revoked_at` set, digest cleared) and its active transfers (status `revoked`, stream lease cleared); suspending leaves grants and transfers in place because start and stream rechecks reject on entitlement status, so a dispute won inside the transfer hour restores the same session — while a full refund that landed during the dispute keeps the entitlement revoked after the win. Each transition kind writes one timeline entry (`entitlements_revoked` / `entitlements_suspended` / `entitlements_restored`, with counts and reasons) sourced from the triggering fact plus one platform audit; a sync that changes nothing writes nothing, so provider redeliveries and outcome replays stay silent. Spent download allowances are never returned by revocation (deliberate staff resets remain T053) and already-transferred bytes are never claimed recallable. Privileged staff still must pass 2FA. `GET /` remains 503. Live Stripe refunds and disputes were not executed in this environment. Run `bin/php artisan test --filter=FulfillmentRevocation`.

Staff with `fulfillment.manage` and a fresh 2FA session manage download access from the admin order detail's Downloads section. `POST /admin/orders/{id}/entitlements/{entitlementId}/update` grants that one buyer a strictly newer ready version of the same purchased file (`GrantAssetUpdate`): only the entitlement's pin moves — the order line keeps the version frozen at purchase, other buyers keep theirs, and downgrades, non-ready versions and other assets' versions are rejected. `POST /admin/orders/{id}/entitlements/{entitlementId}/reset-limit` deliberately restores the allowance (`ResetDownloadLimit`): `downloads_used` returns to zero and the limit may be replaced within 1..1000; a reset that would change nothing is rejected. Both actions require a reason and a staff idempotency key (replay returns the recorded result, a changed payload conflicts), refuse revoked or expired entitlements, and write an order timeline entry plus a platform audit; revocation itself never returns spent allowance. The detail read model lists each entitlement's current and purchased versions, allowance counters and grantable newer versions, never storage keys. Media cleanup (`CleanMedia`) never purges a media asset referenced by a digital asset version, in addition to the `restrictOnDelete` foreign keys. Privileged staff still must pass 2FA. `GET /` remains 503. Live Stripe is not involved in this slice. Run `bin/php artisan test --filter=FulfillmentAssetUpdate`.

## Contact preferences and suppression

Verified contact identity, purpose grants and suppressions are shared platform facts (`delivery_contacts`, `purpose_grants`, `delivery_suppressions`, migration 000054) written only through `UpdateDeliveryPreference`. Consent is purpose-scoped (`cart_recovery`, `newsletter`, `stock_alert`, `price_alert`) with provenance on every fact — source, notice revision (`2026-10-v1`) and verification evidence — and one platform audit per real transition; grants require a verified contact, and replays of grants, revocations, suppressions and provider feedback are silent no-ops that change nothing twice. `DeliveryPolicy` is the one policy marketing and watchlist consumers must consult: `marketingAllowed` requires a verified contact, an active grant for the purpose and no active global or transport suppression; `essentialAllowed` classifies the transactional templates (`order-receipt`, `shipment`, `download-access`, `customer-challenge`) that marketing suppression can never block, so a globally suppressed contact still receives receipts and download access. Provider feedback (`complaint`, `hard_bounce`) suppresses globally and no grant can ever clear it; an `opt_out`/`manual` global suppression is cleared only by the contact's own deliberate grant through a protected verified channel (`preference_center`, `double_opt_in`), never by imports or replays.

The signed one-click unsubscribe is the single deliberate CSRF exception (`preventRequestForgery(except: ['preferences/unsubscribe'])`): tokens are stateless purpose-scoped HMAC payloads (`UnsubscribeTokens`), applying one only ever revokes its one purpose, and tampered or retargeted tokens fail closed with 404. Landing GETs — including mail-scanner and prefetch GETs — only render the confirmation form and never mutate consent; the form POST and provider one-click POSTs (token in the body or the URL query, `List-Unsubscribe=One-Click`) are cookie-free and replay-safe. Every other preference edit stays protected: the account preference center at `/account/preferences` sits behind the customer session and re-proves identity inside the edit transaction, and an unverified customer is refused. The center's stop-all control revokes every purpose and records a global `opt_out` suppression, and turning a purpose back on there is the deliberate act that clears it. Run `bin/php artisan test --filter=MarketingPreferences`.

## Saved products (wishlist)

Saved products are one list per owner (`wishlists` + `wishlist_items`, migration 000055), where the owner follows the same identity model as the cart: a signed-in customer owns an account list that synchronizes across devices, and a guest's saves live server-side under the SHA-256 hash of the anonymous session token — durable across requests while the session cookie survives, never enumerable, and never cross-device until a login merge moves them into the account. `SaveWishlistItem` owns save/remove: saving is a set operation at the variant level (a repeat save keeps one row and refreshes `saved_at`, the intent the merge compares), only a listed variant — a published product's listed variant — can be saved, and a product save resolves to the catalog's default variant. Out-of-stock listed variants stay savable; stock is a display fact, not a save gate. Saving never creates a delivery contact, a purpose grant or a suppression row: a save is not a marketing opt-in (SHOP-02), and watch subscriptions are a separate later slice.

`MergeWishlist` runs beside the cart merge inside `CustomerSession::establish()`: the union is keyed by variant, a variant saved on both sides collapses to the account row keeping the newest `saved_at`, guest-only variants move across untouched, an empty or guest-only list is consumed or reassigned, and repeating the merge on later logins is a no-op. Logout never deletes account saves; the next session simply resolves to a fresh empty guest scope. `ReadWishlist` always shows the catalog's current price and availability for listed entries; when a saved product is unpublished or archived, or its variant is unlisted, the entry degrades to a bare placeholder carrying only its id, state and saved date — title, SKU, price, slug, image and identifiers are withheld — while the save stays durable and returns in full if the product is republished. The storefront surface is `GET /wishlist`, `POST /wishlist/items`, `POST /wishlist/items/{itemId}/delete` plus the `/store-api/v1/wishlist` equivalents, all `no-store, private`, and the product page offers "Save for later" beside the cart form. Run `bin/php artisan test --filter=ShoppingToolsWishlist`.

## Watch subscriptions (stock and price alerts)

Watch subscriptions are one row per (delivery contact, variant, alert type) in `watch_subscriptions` (migration 000056), where the alert types map one-to-one onto the shared delivery purposes (`stock` → `stock_alert`, `price` → `price_alert`). A subscription is the per-variant expression of an opt-in, never a consent store: `SubscribeToWatch` writes consent only through `UpdateDeliveryPreference`, so the two alerts are separate opt-ins and subscribing to one never grants the other. Saving a wishlist item creates no contact, grant, subscription or intent — a save is not an opt-in.

An unverified contact subscribes into `pending` rows and is granted nothing. `VerifyWatchEmail` issues the emailed challenge in the platform's digest-only idiom (SHA-256 digest only, email-digest binding, 24-hour expiry, re-issue revokes the previous challenge, a queued `watch-verification` mail intent per issue; no SMTP is sent by this slice), and consuming it is the double opt-in: one transaction marks the contact verified, grants the pending purposes with `double_opt_in` provenance, activates the rows and snapshots each price row's baseline from the variant's then-current purchasable price (`baseline_amount`/`baseline_currency`/`baseline_exponent`, the baseline T057 compares against). Consumption nulls the digest, so replaying a spent, tampered or expired token fails closed with the same 404 and changes nothing. An already-verified contact subscribes active in-session with `watch_options` provenance — deliberately not a protected source, so subscribing can never clear an `opt_out`/`manual` suppression — and a signed-in customer whose account email is verified has the contact marked verified with `customer_account` evidence, mirroring the preference center. The storefront pair is scanner-safe: `GET /watch/verify` only renders the confirmation form and never consumes; the explicit CSRF-protected `POST /watch/verify` consumes exactly once. Subscriptions attach only to listed variants (published product, listed variant) under the wishlist's generic failure, and `ReadWatchSubscriptions` reports lifecycle and alertability separately — alertability is `DeliveryPolicy` consulted live, so a signed purpose unsubscribe or a provider suppression makes a watch non-alertable without rewriting it — while unpublished or unlisted entries degrade to the wishlist's privacy-safe placeholder. The signed unsubscribe is the shared purpose-scoped token pair from the contact-preferences slice; there is no watch-specific unsubscribe surface. The product page offers "Set alerts" beside the save form (native form, progressively enhanced by `WatchOptions.vue`). Run `php artisan test --filter=ShoppingToolsSubscription`.

Watch alert delivery (T057) starts from the merchant write paths, never from the checkout reservation lifecycle: `EvaluateWatchEvent` is invoked by `AdjustStock` when an adjustment moves the committed available position (on_hand − reserved) from none to some, by `AllocateInventory::restock` under the same transition rule, by `SaveVariants` for price on every save (and for stock when a variant's listed flag flips on), and by `SaveProduct` for saves landing in `published` (stock only when the save enters publication). Holds, commits, releases and shipments get no hook, so a transient reservation release can never alert; eligibility always reads the committed position. An intent lands in `watch_alert_intents` (migration 000057) only for an `active` subscription whose contact passes `DeliveryPolicy` at evaluation time and whose condition holds against current state — for price, the current purchasable price strictly below the activation baseline with identical currency and exponent. Dedupe is per subscription + catalog event (the unique intent key names the merchant operation), and the SHOP-04 cap allows one alert of each type per variant/recipient per 24 hours, counted over `queued`/`sending`/`sent` intents; `cancelled`/`failed` intents never consume the cap. `SendWatchAlert` runs `DeliverWatchAlert`, which rechecks everything immediately before sending — subscription still active, policy still allows, variant still listed, condition still true — and cancels the intent with the failed check as its error code instead of sending; the mail renders title, current price and product link from state read in the claim and carries the signed purpose unsubscribe link. Transport failure finishes the intent `failed` visibly. Run `php artisan test --filter=ShoppingToolsAlert`.

Product comparison (T058) is a pure read model: `GET /compare` and `GET /store-api/v1/compare` take `items` (variant ids) and `products` (product ids) query lists, and `CompareProducts` resolves them exactly as wishlist saves resolve — a product names its default listed variant, the same variant twice is one column, and invalid, unpublished or unlisted selections are removed with a generic notice that carries no catalog facts (removals leaving fewer than two columns fail with the same generic wording). Semantic identity is the catalog's global attribute definition: one semantic key has exactly one type, unit and comparison meaning platform-wide, so a row is a `comparable` definition from the union of the selections' schema versions, never a label match across keys. A value a product never stored, or an attribute its schema does not define, renders as an explicit "Not specified" absence. Numeric cells normalize through `UnitConversions` — a typed registry over the mass (base g), volume (base mL) and length (base mm) dimensions — to the canonical base unit before comparison, and `differs` is decided on the normalized values; units outside the registry keep their own unit as the normal form rather than comparing wrong. Compatibility is the schema versions' `comparison_group`: selections spanning more than one group (a schema-less product is its own null group) expose only the platform basics — price, availability, SKU, type — with `specialized_attributes_omitted` and a plain reason. The selected variant's own price, SKU, availability and option label form the column basics; typed attributes are product-level in the catalog model, so no variant attribute override exists. The compare tray and table UI (T059) sit on top of that read model without changing it. The tray holds at most one selection per product and at most four products — a product/card control names the product and the model resolves its default listed variant, a product-page control names the selected variant — and adding a fifth product is refused with an announced message rather than dropping the oldest entry. The tray persists in a first-party session cookie carrying only the selections, the same cookie-scoped scope as the anonymous guest session that keys the guest cart and wishlist; every page load re-reads it, and the comparison table syncs it from the served comparison. The table's differences-only toggle filters on the model's own `differs` flag (decided on normalized values, never on display strings), remove/replace re-fetch the JSON endpoint with the remaining variant ids and fall back to a full page load when the fetch fails, and a removal that would leave one column renders an add-another prompt instead of requesting a comparison the model refuses. Replace candidates (published products resolved to their default listed variant) and the cart revision are supplied by the controller to the HTML surface only, so each column keeps a working add-to-cart form; the JSON surface stays the pure read model. At the theme's 760px breakpoint the table stacks: each row becomes a block and every value cell carries its column title as a visible label, so nothing scrolls horizontally or truncates at 360px. State changes are announced through `role="status"` regions. Run `php artisan test --filter=ShoppingToolsCompare` and `npm run test:unit -- --run`.

The shopping-tools integration gate (T060) adds no surface of its own: `tests/Feature/ShoppingToolsGateTest.php` drives the save→login merge→compare→cart and subscribe→verify→restock→alert→product journeys end to end over the real storefront controllers and merchant write paths, and `tests/Feature/ShoppingToolsIsolationTest.php` proves interleaved customer and guest sessions never share wishlist, comparison or subscription state, and that unpublishing a product mid-journey degrades the wishlist, product page, comparison and alert delivery consistently. The matching browser journeys are `tests/Browser/wishlist.spec.ts` and `tests/Browser/comparison.spec.ts`, authored with fixture preconditions in-file; no combined PHP/Node Chromium harness exists in this environment yet, so they are not executed locally. Run `php artisan test --filter=ShoppingTools`.
